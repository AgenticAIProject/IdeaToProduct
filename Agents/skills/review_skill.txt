Review Methodology (apply in this order, stop adding items once you have the top 5 defects):

1. EVIDENCE FIRST
   Start from the test result. If tests failed, read the failure output and name the file and behavior that
   caused it. Decide: code defect, dependency/manifest defect, or test-infrastructure problem
   ([TEST-INFRA], [DEPENDENCY], timeout). Only code and manifest defects go to `defects`.
2. REQUIREMENT COVERAGE
   For each Must requirement and its acceptance criteria, find the code that implements it.
   Missing or clearly wrong = defect. Partial but working = feedback.
3. CONTRACT CHECK
   Compare the design's endpoints/fields/status codes (or functions/exports) with the code.
   A mismatch with the design is a defect (cite the design id).
4. RUNNABILITY
   Syntax/import errors, imports of modules not generated or not in the manifest, missing entrypoint.
5. SECURITY BASICS
   Hardcoded secrets, string-built SQL, unvalidated input, unrestricted file upload.
6. VERDICT
   Reject only for real defects from steps 1-5. Style, naming, extra tests, docs polish -> feedback.
   Every defect: "<file>: <what is wrong>; expected <what> (<AC/FR/design id>)".
